# BESMA 안전보건 통합관리 플랫폼 — 벤더 중립 시방서

**문서 성격**: 스마일소프트 개발·내부 개발 전환 시 동일하게 구현 가능한 요구사항 문서.  
**본문**: 요구사항(WHAT) 및 검수 기준(AC)만 기술.  
**부록**: 특정 기술스택/벤더/클라우드/라이브러리 지시(How)는 「부록: 권장 구현안」으로 분리.

# 본문 — 요구사항 및 검수 기준

## 1. 적용 범위 및 목적

### 1.1 적용 범위

- 본 시방서는 **부현전기 안전보건 통합관리 플랫폼(BESMA)** 의 기능·데이터·권한·보관에 대한 요구사항을 정의한다.
- 건설·제조 현장의 안전보건 업무 디지털화, 본사–현장–근로자 간 실시간 안전 정보 공유 및 통합 관제를 범위로 한다.
- 중대재해처벌법·산업안전보건법·위험성평가 의무 대응을 지원하는 기능을 포함한다.

### 1.2 목적

- 요구사항(WHAT)과 검수 기준(AC)만으로 검수 가능한 시방을 제시한다.
- 구현 주체(외주·내부)와 무관하게 동일한 산출물 검수가 가능하도록 한다.

## 2. 용어 및 고정 정책

### 2.1 Role 정의

| 문서/화면 | 설명 |
|-----------|------|
| HQ_ADMIN | 본사 관리자. 전체 현장 모니터링, 표준 DB·결재·통계·예산 편성/통제. |
| SITE_ADMIN | 현장 관리자. 소속 현장 데이터·작업지시·TBM·점검·사용실적 입력/조회. |
| WORKER | 근로자. 작업지시 수신·확인·서명, 위험요인신고·작업중지. |

### 2.2 고정 정책 (변경 불가)

| 구분 | 정책 | 검수 기준(AC) |
|------|------|----------------|
| 예산 | 본사: 편성/통제. 현장: 당 현장 사용실적 입력·조회만. | 현장 계정으로 예산 편성·배정·승인 화면/API가 노출되지 않아야 한다. 본사 계정으로만 예산 편성·통제 기능이 제공되어야 한다. |
| 네이버웍스 | 품의 연동은 **메일 제목(Subject) 수집만**. 본문·첨부·결재선 연동 금지. | 품의 목록에 본문/첨부/결재선을 파싱·저장하는 기능이 없어야 한다. Subject(제목)만 저장·표시되어야 한다. |
| 앱 | 근로자용·관리자용 2종. 근로자 홈에 ‘작업중지’와 ‘위험요인신고’가 **서로 다른 별도 버튼**으로 존재. | 근로자 앱 홈에 작업중지용 버튼 1개, 위험요인신고용 버튼 1개가 각각 구분되어 노출되어야 한다. 관리자 앱 홈에는 위 두 기능이 직접 노출되지 않고, 메뉴 진입 후 사용되어야 한다. |
| GPS | 수집: 가변 주기(정지/이동/지오펜스/이벤트). 저장: 3개월 일반 보관 + 5년 압축 보관. | GPS 로그가 3개월 이상 일반 조회 가능 형태로 보관되어야 하고, 5년간 압축 보관 정책이 적용되어야 한다. |

## 3. ERP 영역과 안전 영역의 경계

### 3.1 요구사항

- 안전 모듈은 **ERP의 Site(현장) 마스터·User(사용자) 마스터의 식별자(키)만 참조**할 수 있다.
- 안전 모듈이 ERP의 예산 편성·재고·인사 급여 등 업무 데이터를 직접 조회·변경해서는 안 된다.
- 작업지시의 개인별 배정이 ERP에서 오는 경우, 안전 모듈은 **해당 사용자 키·현장 키**만 수신하여 작업지시·서명·TBM과 연결하여야 한다.

### 3.2 검수 기준(AC)

- 안전 플랫폼 DB/API에 ERP Site ID·User ID(또는 동의된 외부 키) 이상의 ERP 마스터 필드를 저장·노출하지 않아야 한다(필요 시 계약서별 예외 정의).
- ERP에서 “작업지시 자동 생성” 연동 시, 안전 플랫폼이 수신하는 payload는 현장 식별자·대상 사용자 식별자·작업 개요 등 안전 업무에 필요한 최소 항목으로 한정되어야 한다.

## 4. 공통 요구사항

### 4.1 권한(RBAC)

- 모든 기능은 **역할(Role) 기반 접근 제어**가 적용되어야 한다.
- HQ_ADMIN / SITE_ADMIN / WORKER에 따라 **메뉴 노출·API 호출·데이터 조회 범위**가 구분되어야 한다.
- 현장 데이터는 **소속 현장 단위**로만 SITE_ADMIN이 접근할 수 있어야 한다. 본사는 전체 현장 조회 권한을 가져야 한다.

**AC**: 동일 API라도 Role·소속 현장에 따라 반환 데이터 또는 HTTP 403이 구분되어야 한다.

### 4.2 로그·증빙

- **전자서명(작업지시 확인·완료·TBM 서명)** 발생 시 서명 시각·사용자 식별자·연관 엔티티 ID가 저장되어야 한다.
- **작업 완료(서명·사진)** 시 서버 수신 시각·위치 정보(GPS) 정책에 따른 저장이 이루어져야 한다.
- **관리자 동작**(작업지시 배포·결재·점수 입력·시정조치 배정 등)에 대해 **누가·언제·무엇을** 수행했는지 감사 로그가 기록되어야 한다.

**AC**: 검수 시 기간·사용자·기능별 로그 조회가 가능해야 한다.

### 4.3 보관 정책

- **GPS 로그**: 3개월 일반 보관, 5년 압축 보관. (고정 정책)
- **전자서명·작업지시·TBM·위험신고·의견청취·점검·시정조치** 등 핵심 안전 데이터는 **법정 보존 기간**에 맞춰 보관 정책이 정의되어야 하며, 삭제 시에는 삭제 로그가 남아야 한다.

**AC**: 보관 정책 문서가 존재하고, 조회/삭제 시 해당 정책이 적용되어야 한다.

### 4.4 오류 케이스

- **네트워크 단절 등으로 저장 실패** 시 사용자에게 실패 사유가 표시되어야 하고, 재시도 또는 오프라인 저장 후 동기화 경로가 제공되어야 한다.
- **권한 부족** 요청 시 403 등 명확한 응답과, 필요 시 “권한이 없습니다” 메시지가 노출되어야 한다.
- **필수 입력 누락·형식 오류** 시 저장이 거부되고, 어떤 항목이 잘못되었는지 식별 가능해야 한다.

**AC**: 위 오류 상황별로 정의된 동작과 메시지가 구현되어 있어야 한다.

## 5. 채널별·기능별 요구사항 및 검수 기준

### 5.1 근로자 앱 (WORKER)

#### 5.1.1 홈

| 구분 | 요구사항 | 검수 기준(AC) |
|------|----------|----------------|
| 입력 | 없음(진입 시점). | — |
| 처리 | 금일 작업지시 상태를 집계하여 오늘 작업요약을 구성한다. | 오늘 작업요약에 금일 작업지시 건수·확인/미확인·완료 상태가 반영되어야 한다. |
| 출력 | 오늘 작업요약, 작업중지 버튼, 위험요인신고 버튼. | 작업중지와 위험요인신고가 서로 다른 별도 버튼으로 출력되어야 한다.(고정 정책) |
| 권한 | WORKER. | 본 채널은 근로자 역할로만 접근 가능해야 한다. |
| 로그/증빙 | 버튼 클릭 시 진입 로그. | 작업중지·위험요인신고 진입 이력이 기록되어야 한다. |

| 구분 | 요구사항 | 검수 기준(AC) |
|------|----------|----------------|
| 입력 | 작업지시 ID, 위험요인/대책 확인 여부, 전자서명 데이터. | 서명 시 시각·사용자·작업지시 ID가 서버에 전송되어야 한다. |
| 처리 | 서명 데이터 검증 후 저장. 작업지시 상태를 “확인함”으로 전이한다. | 상태 전이: 미확인 → 확인함. 한 번 확인된 작업지시는 동일 사용자에 대해 재확인 정책이 정의되어야 한다(덮어쓰기 허용 여부 명시). |
| 출력 | 작업지시 상세(작업 내용·위험요인·대책), 서명 완료 여부. | 위험요인·대책이 노출되어야 하고, 확인 서명 완료 후 완료 상태가 출력 가능해야 한다. |
| 권한 | WORKER(본인 소속 작업지시만). | 타인 작업지시 목록/상세가 노출되지 않아야 한다. |
| 오류 | 서명 미입력·네트워크 오류. | 서명 미입력 시 저장이 거부되어야 한다. 네트워크 오류 시 재시도 또는 오프라인 저장 후 동기화 안내가 있어야 한다. |
| 로그/증빙 | 확인 서명 시각·사용자·작업지시 ID·위치(GPS 정책 적용) 저장. | 검수 시 서명 이력 조회가 가능해야 한다. |
| 보관 | 서명·작업지시 데이터는 법정 보존 기간 적용. | 보관 정책에 따라 조회·보관이 가능해야 한다. |

#### 5.1.3 작업 종료(서명 + 사진)

| 구분 | 요구사항 | 검수 기준(AC) |

| 처리 | 완료 서명·사진 수신 후 작업지시 상태를 “종료”로 전이. GPS는 가변 주기 정책에 따라 저장. | 상태 전이: 확인함 → 종료. 사진 파일이 서버에 저장되고 작업지시와 연결되어야 한다. |
| 출력 | 완료 여부, (선택) 사진 미리보기. | 완료된 작업에 대해 완료 시각·사진 열람이 출력 가능해야 한다. |
| 권한 | WORKER(본인). | 본인 작업만 종료 처리 가능해야 한다. |
| 오류 | 사진 누락·용량 초과·전송 실패. | 사진 필수 시 누락이면 저장이 거부되어야 한다. 용량·형식 제한이 정의되고 오류 메시지가 표시되어야 한다. |
| 로그/증빙 | 완료 시각·사용자·작업지시 ID·GPS(정책)·사진 메타데이터. | 검수 시 완료 이력·사진 조회가 가능해야 한다. |

### 5.2 관리자 앱 (SITE_ADMIN 용도)

#### 5.2.1 작업지시(생성/배포·현황·개인별 서명 확인)

| 구분 | 요구사항 | 검수 기준(AC) |
|------|----------|----------------|

#### 5.3.4 문서함·예산(현장)·인력/조직·설정

# 부록 A: 권장 구현안 (How)

*본 부록은 특정 기술스택/벤더/클라우드/라이브러리에 대한 권장사항이며, 본문 요구사항을 만족하는 한 다른 방식으로 구현 가능하다.*

## A.1 기술스택 권장

- **프론트엔드**: SPA 또는 하이브리드 앱. 웹은 반응형 또는 데스크톱 전용. 앱은 근로자용·관리자용 2종 분리 빌드/배포.
- **백엔드**: REST 또는 동등한 API. 인증·세션·RBAC은 서버에서 일원 관리.
- **DB**: 관계형 DB로 트랜잭션·감사 로그·보관 정책 적용. GPS·대용량 로그는 시계열/압축 저장 검토.
- **클라우드**: 퍼블릭/프라이빗 선택은 계약·보안 정책에 따름. 단일 리전·멀티테넌트(현장/조직 단위) 구조 권장.

## A.2 외부 연동 권장

- **ERP**: Site ID·User ID 등 최소 키만 연동. 작업지시 자동 생성 시 안전 쪽 수신 API·payload 형식 정의.
- **네이버웍스**: 메일 Subject 수집만. IMAP/API 등으로 제목(Subject) 필드만 파싱·저장.
- **지도**: 현장 위치·SOS 표시용. 카카오맵/네이버/구글 등 계약에 따라 선택. 클라이언트에서 “마지막 저장 위치만 표시, 강제 푸시 시에만 업데이트” 규칙 적용.
- **알림**: 푸시·SMS/알림톡. 비상(SOS) 시에만 SMS/알림톡 사용 권장(SENS 등).

## A.3 음성·OCR·번역 권장

- **음성**: 클라이언트 로컬 STT(예: Web Speech API)로 변환 후 **텍스트만** 서버 전송. 서버에 음성 원본 저장하지 않음(요구사항).
- **OCR**: 서류 인식 시 선택 호출. CLOVA OCR 등 벤더 선택 가능. 호출 로그·결과 텍스트 저장.
- **번역**: TBM 공지/긴급 알림 다국어 시 선택. Papago 등. 고도화 섹션으로 분리 가능.

## A.4 GPS·오프라인 권장

- **GPS**: 수집 주기(정지/이동/지오펜스/이벤트)는 클라이언트 또는 서버 정책으로 가변 설정. 저장 시 3개월 일반·5년 압축 보관 정책 준수.
- **오프라인**: 필수 데이터(작업지시·서명·신고)는 로컬 저장 후 통신 복구 시 동기화. 충돌 시 서버 우선 또는 타임스탬프 기반 규칙 정의.

## A.5 보안·다중 테넌트 권장

- **인증**: SSO 또는 ID/PW+세션. 역할(Role)은 서버 세션/토큰에 포함.
- **RBAC**: 역할·권한·리소스(메뉴·API·현장) 매핑 테이블 유지. API 호출 시 Role·소속 현장으로 필터링.
- **다중 테넌트**: 조직/현장 단위로 데이터 격리. Site ID 기반 쿼리 필터 필수.
